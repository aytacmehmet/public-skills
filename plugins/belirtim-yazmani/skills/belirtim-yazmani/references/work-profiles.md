# Work profiles

Read for intake, profile selection, capacity, native child dispatch, hooks, model suggestions or resume. This is a private production protocol; its commands, model names and receipts never belong in developer handoff files. Resolve `../../scripts/bv2.py` from the absolute loaded skill directory. The host runs the commands below using that absolute quoted path and an explicit workspace path; no plugin-root cwd is assumed.

## Common quality and profile separation

`work_profile` changes preparation intensity and scheduling. Existing document `--profile hafif/standart/tam` still controls applicable specification sections. A low work profile never removes required content, asset checks, human approval or final readers. Preserve A-F, the private 3.1 reader protocol, three full-scope independent readers per round, two consecutive clean current-snapshot rounds, actual visual evidence where required, and the code-free plan/architecture gate. The public handoff schema remains 3.0.

| Work profile | Conditional preparation attempts | Concurrent children | Reviewer attempts per episode | Total child attempts per episode | Typical scope |
| --- | ---: | ---: | ---: | ---: | --- |
| `Lite / Yalın` | 0 | 1 | 12 | 12 | Clear small field or rule change |
| `Plus / Gelişmiş` | 1 | 1 | 12 | 13 | Small UI/service contract |
| `Pro / Yetkin` | 2 | 2 | 12 | 14 | Several objects or screens with dependencies |
| `Max / Doruk` | 4 | 3 | 12 | 16 | Critical change, multiple contracts or owners |
| `Ultra / Üstün` | 6 | 3 | 12 | 18 | Dense cross-authority rollout and uncertainty |

These are ceilings, not agent targets. Six actual reviewer dispatches are necessary if the first two rounds are clean. The existing four-round final protocol ceiling also applies. Failure, timeout, cancellation and retry consume attempts; revisions and model changes never reset the episode ledger. The writer, tools, hooks and correction costs are additional. The lower of profile and observed host capacity applies, with a shared ceiling of three children in one coordinated run. Linked workspaces must use one coordinator file; unrelated jobs using other registries are outside this enforcement, so the host skill must explicitly account for their occupied slots. If another authorized task occupies a slot, wait; do not create nested agents or increase the quota.

## Intake and one selection card

1. Read current sources/baseline and decision ownership before scoring. Run `work-profiles catalog` for the machine-readable profile catalog.
2. Make an assessment JSON file with `size`, `complexity`, `dependencies`, `uncertainty`, `impact` and `evidence_gap`, each 0..4 or null, either at the root or under `factors`. Prefer `{ "score": 2, "rationale": "...", "source": "actual source/pointer" }`; a bare score is a declared assessment, not validated evidence. Optional `counts` contains requirements, objects and assets; the CLI binds counts to complete requirements/objects and the actual physical asset/dependency-contract inventory, including reference inputs beyond PNGs. Optional `preparation_blockers` lists unresolved business/source contradictions.
3. Run `work-recommend <workspace> --assessment <assessment.json>`. Present the recommendation and user choices together in one card, in the user's language. Include rationale/source pointers, assessment completeness/possible profiles, capacity, conditional attempt limits, the common quality floor, and the model suggestion with access uncertainty. Avoid a second technical questionnaire for routine implementation choices.
4. Record the actual user's choice with `work-select <workspace> --profile lite|plus|pro|max|ultra --assessment <assessment.json> --capabilities <capabilities.json> --capacity <capacity.json> --receipt <actual-selection-receipt> --confirmed`. Use `--coordinator <shared-file>` for linked workspaces in one run; the default is `.byw-dispatch.json` in the workspace's parent. The flag attests an already given choice; never manufacture a receipt. Selection creates private state, not an agent/model call or business/default/specification approval.

The weighted score is `size + 2*complexity + 2*dependencies + 2*uncertainty + 3*impact + 2*evidence_gap`, range 0..48. Bands are 0..8 Lite, 9..17 Plus, 18..28 Pro, 29..38 Max, 39..48 Ultra. Impact >=3 raises the floor to Max; dependencies=4 and impact>=3 raises it to Ultra; size>=3 raises the capacity recommendation floor to Pro. Counts calibrate size using requirement/object/asset maxima 10/3/3, 25/8/8, 60/20/20 and 120/40/40, then 4 above them; use the highest category. These initial thresholds are design assumptions, not provider performance measurements.

Unknown factors stay null. Compute score bounds and possible profiles by enumerating values with all floor rules; do not turn a score range directly into adjacent bands. For dependencies=4 and unknown impact, Lite/Plus/Ultra may all be possible. Missing facts do not become low risk. With an explicitly selected profile the single writer can close missing inputs while capacity is PENDING/BLOCKED or assessment/isolation/vision is incomplete. Actual preparation child dispatch still needs PASS capacity and host child limits; final review/release waits for all required criteria. Explicit unresolved business/source contradictions block preparation until resolved. A bounded ABAP_DEVELOPER implementation choice may remain open under existing rules.

Honor a lower explicit selection without quietly changing it. If the required work exceeds its budget or capacity, explain the concrete gap and wait for the user's split, higher-profile or new-budget decision. Profile selection does not waive any quality gate. Elapsed time is not consent.

## Capacity and native execution

Capabilities JSON declares `host` (`codex`, `claude` or `manual`), `reader_isolation`, `vision`, `child_limit` (1..3), and optionally `model_catalog`. Capability snapshots describe observed host support; account access and actual invocation are separate evidence. Unobserved capabilities remain explicit gaps. Do not infer cloud hook support from local plugin discovery.

Capacity JSON declares `status` (`PASS`, `PENDING` or `BLOCKED`) with its reason/evidence. A PASS request also needs positive integer `context_limit`, `packet_tokens` and `output_reserve` plus a nonempty `evidence` reference; required images need an independently estimated positive `image_tokens`. The CLI bounds the actual serialized reader envelope including its reference content and packet overhead, adds separately estimated image cost, verifies complete response reserve, enforces the initial 20% context margin and binds the current specification, physical input and checker fingerprints. It records `measurement_kind=ESTIMATED`; the conservative text-byte bound is not observed tokenizer/provider usage. A PASS declaration alone is not provider execution proof. Each final reader must fit the complete required packet, all requirement/plan replies and required images. Unmeasured capacity is PENDING; insufficient capacity is BLOCKED. Preparation slicing does not replace full-reader coverage. New reader aggregation needs a separately reviewed protocol. Refresh selection/capacity when bound input or checker hashes change, retaining the existing episode and costs; do not relabel stale capacity current. Supply `--assets-root <actual-input-directory>` to work commands when physical files live outside the workspace's parent.

The skill owns native host orchestration; the deterministic CLI reserves/adopts evidence and never auto-launches a model subprocess. Use this sequence:

1. `work-status <workspace>`: inspect recommendation, selected profile, readiness, limits, usage, active attempts and issues; `execution_evidence` is recorded data, not provider authentication.
2. `work-admit <workspace> --operation prepare` before a conditional preparation job; `--operation review` before final reader work. Correct the reported PENDING/BLOCKED criteria before dependent execution. Admission does not approve business decisions or release.
3. `work-begin <workspace> --task-id <logical-task> --role prep|reviewer --input-sha256 <actual-packet-hash> --context-id <fresh-context-id>` before dispatch. Context identity is required for both preparation and reviewer roles. After two consecutive FAIL/UNKNOWN attempts for the same logical task, `--diagnosis <actual-investigation>` is required before a third attempt; it records the tested explanation/change in method, not human approval or business acceptance. A reserved RUNNING attempt is charged even if dispatch subsequently fails. Check both local profile limits and shared session occupancy before calling the host.
4. Native dispatch uses a fresh isolated context and a bounded packet, never a fork of the writer conversation. Set `BYW_WORKSPACE` to the actual private workspace for the adapter, and pass a strict JSON prompt `{ "byw_task": { "task_id": "issued ID", "attempt_id": "reserved attempt ID", "context_id": "fresh context ID", "input_sha256": "actual packet hash" }, "packet": "issued packet content" }`. These are actual routing/binding values, not new approval or source authority. The recognized native leaf role and RUNNING ledger supply the role/episode; the hook also checks the shared coordinator's matching RUNNING workspace/episode/attempt/task reservation. The selected capabilities' `coordinator_file` is mandatory for managed native dispatch and is supplied by work-select. Native PreToolUse requires the actual `tool_use_id` and atomically claims that already charged reservation in the explicitly selected external coordinator. Repeating the same host/event ID is idempotent; a different native call ID cannot reuse the attempt. This callback writes only the coordinator reservation, never the workspace specification or user configuration. Preparation agents have read-only evidence authority. Reviewers use the issued 3.1 packets; all requirements remain mandatory. Take the stable logical task ID `review:<round>:<reader_id>` from the packet's `work_task.task_id`. Failed execution may retry this same logical task using a new charged attempt, fresh request packet/hash and fresh context; it does not reset prior attempts or reuse failed contexts. Packet creation by eval-request does not reserve or start all readers: Lite/Plus dispatch them sequentially, reserving and finishing each actual attempt. Never pass peer verdicts, including across rounds, or give leaf agents permission to spawn children.
5. `work-finish <workspace> --task-id <issued-task> --status COMPLETED|FAIL|UNKNOWN|CANCELLED --input-sha256 <issued-packet-hash> --context-id <issued-context> --response-sha256 <actual-response-hash> --receipt <actual-host-receipt>`; retain the issued `--attempt-id` when retry binding is needed. Exact input/context identity is mandatory even for UNKNOWN. Preserve null, partial, timeout and malformed responses as failures/UNKNOWN; never drop them from aggregation. COMPLETED is recorded as a passed execution receipt, not semantic acceptance. Existing eval-record/confirm-reviews still validate actual reader content and human confirmation, and managed admission crosschecks its packet/context/response bindings against the ledger.
6. Recheck `work-admit <workspace> --operation release`, then the unchanged exact-snapshot final gates and saved ZIP/batch integrity. Explicit release admission applies even when hooks are skipped. Keep private work state outside the public projection.

Logical task IDs are stable across retries; attempt IDs and reviewer context IDs are unique per issued attempt. Repeat result recording for the same finished attempt must not create a new attempt. A later successful attempt may supersede that logical task's failed execution for admission, while the failed attempt and its cost remain recorded. Workspace and coordinator ledgers are locked and atomically saved; crash reservations stay visible and are never auto-expired as successful work. If dispatch crashes after reservation, recover the incomplete task as UNKNOWN with its exact issued input/context identity, preserve its receipt gap and counted cost, and re-admit before retry. Diagnose after two failures of the same method. Never fake a host receipt to clear a slot. Persisted episode identity, outstanding tasks, open decisions and costs survive resume/compact; reload source/hash authority rather than trusting the summary. A new budget episode requires explicit human acceptance and a parent link to preserve prior usage.

## Hook use and fallback

Host adapters are supplementary command hooks around the same admission ledger. Package installation/discovery does not prove native hook execution, trust or cloud interception. Use only synchronous checks for control, a known workspace/operation filter and a small deterministic handler; do not call an LLM on every tool event. Match the actual host envelope and operation, not a generic shell substring. Unsupported or untrusted events use explicit stage CLI checks and report that interception is NOT_RUN/unsupported.

Claude uses `hooks/hooks.json` at the plugin root. Codex uses `hooks/codex.json`, declared by the active `.codex-plugin/plugin.json` manifest's `hooks` field. Portable agent-plugin metadata is preserved separately at `metadata/agent-plugin.json`; the native compatibility patch follows observed Codex 0.160.0 manifest selection. The handlers use a 10-second configured timeout. Windows hook commands use the native runtime's `${PLUGIN_ROOT}` substitution and quoted paths with the runtime's default command shell; do not assume PowerShell environment syntax. Managed native leaf PreToolUse is a scoped coordinator write: it atomically binds the reservation to the actual native call ID to prevent replay; admission, workspace inspection and lifecycle diagnostics remain read-only. Non-operation lifecycle diagnostics use explicitly set `BYW_WORKSPACE`; absence means no target, never guessed cwd authority. PostToolUse reports current fingerprints/profile diagnostics without inventing receipts or silently altering specification authority. Stop reports readiness without a continuation loop. Claude read-only leaf roles are packaged under `agents/`; Codex role files under `agents/codex/` are project opt-in candidates, not proven plugin-discovered agents. No model is pinned by these definitions.

| Purpose | Intended native events | Required invariant |
| --- | --- | --- |
| Identity/capability | SessionStart | Observe identity; no settings or authority changes |
| Role/quota/admission | PreToolUse | Check recognized scoped work before execution |
| Input/spec changes | PostToolUse | Invalidate affected snapshots; no retroactive approval |
| Child receipt | SubagentStop | Check issued task and response shape/hash; semantic review remains separate |
| Context checkpoint | PreCompact/PostCompact | Preserve identity, costs and open decisions; summary is not source authority |
| End | Stop and explicit CLI admission | Report blockers with bounded continuation; never loop indefinitely |

Intended events are a design map; use only events implemented and qualified by the adapter for the observed host. No prompt/agent hook is required for the shared solution. Native event differences must remain explicit. A handler timeout, malformed output or exception cannot yield a fabricated PASS. Core release admission protects the final state independently. PostToolUse/async handlers cannot undo a completed external action. Small admission handlers target 5–10 seconds; expensive deterministic checks run as separate stage commands. Actual defaults/limits come from packaged adapters and their qualification, not this target range. Repeated Stop hooks must honor active/terminal guards and lead to WAITING_USER/STOPPED after the retry limit.

## Provider-local model suggestions

Use the current provider/host's observed model catalog. The private `model_suggestion` refers only to the current host and is `recommendation_only`; catalog observation is availability metadata, not an inference call or confirmed account access. Keep `recommended_model`, `recommended_effort`, available capability and `effective_model` separate. Plugin Max/Ultra are not model reasoning values or a Claude Ultracode toggle. No automatic provider/model/settings switch is authorized by choosing a profile. Model suggestions and cost telemetry are private and never enter the developer ZIP.

| Profile | Codex writer suggestion, when available | Claude writer suggestion, when available |
| --- | --- | --- |
| Lite | gpt-6.1-sol / medium | claude-sonnet-5-5 / medium |
| Plus | gpt-6.1-sol / medium; high for uncertain boundaries | claude-sonnet-5-5 / high |
| Pro | gpt-6.1-sol / high | claude-sonnet-5-5 / high; Opus high for difficult contradictions |
| Max | gpt-6.1-sol / xhigh; gpt-6-astra / high for difficult contradictions | claude-opus-5-5 / high; xhigh for critical probes |
| Ultra | gpt-6-astra / high–xhigh; reassess gpt-6.1-sol / max if unavailable | claude-opus-5-5 / xhigh; claude-fable-5-1 only when observed and justified |

These are the approved design's initial role suggestions, not current account access or quality measurements. Baseline final readers use Sol/high or Sonnet/high when available; stronger critical readers require a reason. Smaller models may do bounded extraction/triage, with returned evidence checked by the writer. Do not silently delegate final acceptance to an unqualified cheaper model. Deterministic hashes/schema/links/inventory need no LLM. Respect product/API reasoning differences and aliases; unknown access/support stays UNKNOWN.

Optimize cost per accepted correct handoff: read unchanged sources once, use check-plan's bound unchanged units, delay final readers until business/reference closure, and give preparation agents narrow packets. Record actual input/output/cache/reasoning tokens, wall time, failed calls and rework only when telemetry exists. An estimated token budget is not an enforced hard limit. Hook contract tests, isolated package discovery and synthetic profiles do not prove provider cost, native routing, hook execution, vision or SAP runtime. Compare profiles against the same quality floor before claiming improvement.
