# Workflow

- **R-BYW-WF-01** Resolve ../../scripts/bv2.py from the absolute loaded skill directory; quote its path. Same core in both hosts. No dependency on local skills/plugins or a fixed developer model. Missing dependencies are a limitation, not a complete delivery.
- **R-BYW-WF-02** Collect stated business/UI decisions, inputs, scoped baseline, naming and approved defaults. Use one workspace per development. Split mixed questions by decision owner; never ask consultant implementation questions. Patch private intake/decisions/open_questions with id, owner, domain, question and grounded options; questions returns consultant items only. Each option needs text, rationale, assumptions and consistency/suitability/quality scores 0..5. At most three, ranked A/B/C by their equal-weight mean. Unknown facts remain gaps; scores cannot approve.
- **R-BYW-WF-03** init/migrate keeps original sources; release-init creates the 3.0 target. For an existing 2.0 delivery workspace use release-upgrade; it preserves baseline identity, remaps asset filenames and resets approvals. Imported content stays reference-only. Keep the complete target, requirement/AC/test/object chains, quantities/units and behavior. Unknown business decisions are never technical defaults.
- **R-BYW-WF-04** Record architecture responsibility boundaries and fixed constraints. developer_decisions contains ABAP_DEVELOPER/IMPLEMENTATION records with question, context, constraints, architecture constraint refs and packaged reference IDs; status OPEN has null answer. They must not change the functional contract. Consultant/system/architecture findings stay blocking. No solution/implementation decision is made automatically.
- **R-BYW-WF-05** Each reference records a prefixed local path, hash, purpose and optional decoded TOON pointer. Supply the referenced content through private assets; source_path may map an original input filename to its public prefixed path. Bundle required external facts/excerpts as neutral local contracts, with complete needed coverage. Never depend on an inaccessible document or URL.
- **R-BYW-WF-06** Use check-plan after intermediate changes. Run only invalidated check units and dependency closure; check-record binds an actual PASS/FAIL to the emitted input hash. This is a private planning cache, not release approval or fresh model evidence. Collect edits and consultant answers before final independent reviews. Existing business approvals/reviews invalidate when the target changes; old receipts stay in private history.
- **R-BYW-WF-07** Updates require verified scoped presence or confirmed absence plus final approved design, not assumed absence. Include exact baseline artifact privately and complete normalized baseline content publicly; keep full target and stable-ID delta. Public file basenames start with development_name; manifest roles identify authority. All delivered versions remain immutable.
- **R-BYW-WF-08** For each dependency keep a private dependency_contracts record: development_id, version, contract, content and requires_change. For a changed partner include its spec_sha256 and source_pointer; content must equal that pointer's complete needed contract. Use a contract section with self-contained data, not a whole unrelated implementation. Changed partners require their own workspaces and ZIPs. Batch checks version/name/source/ownership/rollout consistency and rejects cycles.
- **R-BYW-WF-09** release-approve and confirm-reviews record only genuine current-snapshot human confirmations privately. Run final independent review only when business/design questions, architecture and references are complete; technical bounded choices may remain for the developer. Do not fabricate receipts. Validate actual PNGs and approved offline interactive exceptions; no mockup code is generated here.
- **R-BYW-WF-10** handoff-batch input is TOON with developments entries containing workspace and assets_root paths scoped to the manifest directory. Use --output and --batch-id. All ZIPs are staged, individually verified and published together in one new batch directory; no early final main ZIP. Every ZIP includes its required dependency content and neutral developer starting/decision/acceptance guidance. No producer logs, tools, models or private approvals. verify checks the saved artifacts. feedback reopens the defect and requires a new version.
